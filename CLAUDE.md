# Frase Project Guidelines

This document outlines the coding standards, patterns, and architectural decisions for the Frase project.

This is a language learning app that allows users to save words and phrases for later review based on various learning methods (flashcards). Is also gets AI generated context for the saved phrases and words to help user learn more effectively.

## Core Technologies
- **PHP**: 8.4
- **Laravel**: 12.x
- **Frontend**: Tailwind CSS 3, Blade Components, jQuery (for Ajax), Vite
- **Database**: SQLite (default)

## Core guidelines
- All the code that you will write needs to follow the laravel best practices, standards and primarily be consistent. 
- Although if you find some code that not adheres modern laravel conventions, suggest to change it so it is correct.
- When creating solutions always look for the most efficient way to solve the problem, do not overcomplicate the code.
- Always document any changes did to the application architecture here in this AGENT.md file for future reference. This file is supposed to hold the current architecture of the application and also as a guideline for future contributions so they are consistent with the conventions.
- Stick to the current naming conventions and patterns.
- You don't have to run "npm run build" after implementing new features, because I use hot reload and can see changes in the dev environment.
- **Exception — previewing via the `frase.test` Herd environment:** when the Vite dev server (`npm run dev`) is *not* running, `@vite` finds no `public/hot` file and falls back to the compiled assets in `public/build`. If those are stale, recently added Tailwind classes are missing and styling looks broken (works in production because deploy runs a fresh build). So before previewing `frase.test` without the dev server, either keep `npm run dev` running or run `npm run build` to refresh `public/build`.

## Application Architecture

### Routing
- Routes are defined in `routes/web.php`.
- A mix of **Controller-based routes** and **Route Closures** is used. 
- For complex logic or multi-step processes, prefer Controllers (e.g., `CardController`, `WordboxController`).
- Simple logic or direct view returns often use closures in `web.php`.

### Controllers & Logic
- Controllers often handle validation manually within methods using `$request->validate()` or Form Requests (e.g., `StoreCardRequest`).
- Some business logic is contained within models (e.g., `AI`, `Learning`).
### AI Integration
- AI integration (OpenAI/LLM) is encapsulated in the `App\Models\AI` model.
- **Model & params**: Chat generation uses the `gpt-5.4-nano` model (defined in the `AI::MODEL` constant) via the Chat Completions endpoint with `reasoning_effort` set to `medium` (the `AI::REASONING_EFFORT` constant); latency-sensitive calls (the conversation/challenge turns) pass `low` explicitly instead. Embeddings still use `text-embedding-3-small`. Reasoning models reject `temperature`, so it is never sent. All structured responses use strict `json_schema` response formats.
- **Prompt conventions**: Flashcard prompts keep the system message to the tutor's role/rules and the per-field instructions in the schema property descriptions. Two structural rules are enforced: (1) the `phrase` (term) is the learner's own word — spelling-corrected and reduced to its canonical form (**base/dictionary form** for `lexical`, broken→break; **reusable frame** for `expression`, see Term types); single words are **kept as single words** (no collocation expansion) and existing multi-word phrases are kept as written; (2) the example `sentence` must contain the term wrapped in square brackets exactly once (`[term]`, in whatever inflected form it appears) so the learning blanking regex `/\[.*?\]/` works. Because the nano model drifts, the *shape* rules for `sentence` and `examples` are phrased as explicit negatives in their property descriptions ("never a list", "examples must NEVER contain square brackets", "the bracketed span must be the term itself, never another word"). Each of those negatives was added in response to an observed failure: dropping one makes the model produce full-sentence examples, a 3-line bracketed list in `sentence`, or bracket the wrong word.
- **Term types (`cards.term_type`)**: every card is classified at capture as either `lexical` or `expression` (`Card::TYPE_LEXICAL` / `Card::TYPE_EXPRESSION`, `Card::TERM_TYPES`). The axis is **naming unit vs. ready-made utterance**, *not* word count:
  - **`lexical`** — a naming unit; answers *"X means …"*. Single words (`cabinet`), collocations/compounds (`traffic jam`, `make a decision`) and **idioms** (`under the weather`, `kick the bucket`) are all lexical, because each names a concept.
  - **`expression`** — a ready-made utterance or utterance *frame* performing a communicative function (refusing, requesting, hedging, warning, greeting); answers *"you say X when you want to …"*: `I'd rather not`, `can you hand me the [something]`, `you better be ready`.
  A pasted **full sentence** is not a third type — it is normalized into the reusable frame (`I would like to go to the cinema tomorrow` → `I would like to [do something]`) and classified `expression`. The column is `string` with a DB-level default of `'lexical'`, which backfills existing rows and covers the legacy creation paths (`CreateCardJob`, `CallAIJob`, the manual-create route closure) without touching them. The type is assigned by the AI at capture but is **user-correctable**: `cards/edit.blade.php` renders it as a `<x-forms.select>` and the update route closure validates it with `Rule::in(Card::TERM_TYPES)`.
- **Card fields**: A card stores `phrase` (term), `term_type` (`lexical`|`expression`, see Term types), `translation` (empty for native cards), `example_sentence` (bracketed sentence, powers the Sentences learning mode), `definition`, `theme_id`, and three **usage-example** columns `example_1`/`example_2`/`example_3` — always **unbracketed** short (2-4 word) usage *fragments* (no subject pronoun / no full sentence) each showing a different common use of the term (a different inflected form, a preposition it takes, a collocation/set phrase), rendered as the small **boxes** on the card page. **Both** types get an `example_sentence`; the example phrases are **`lexical`-only** — an `expression` is illustrated by its sentence alone, so the AI returns an **empty `examples` array** for it, `cards/show.blade.php` skips the boxes for expression cards, and `cards/edit.blade.php` **hides** the three "Example phrase" inputs when the type is `expression` (hidden, not removed, so they still submit; a small jQuery handler re-toggles them live off the `term_type` select). The columns are nullable, but for a `lexical` card the AI is prompted to always return exactly 3 — a bare "up to 3" made the nano model return an empty array, and it still occasionally returns `[""]`, which `AjaxController@index` filters out before mapping. It also has a user-editable free-text `note` column (nullable, not AI-generated). There is **no `question` field/mode** (removed). The card **detail page** (`cards/show.blade.php`) renders the `term_type` as small lowercase text immediately left of the language flag, the 3 examples as small boxes below the term (lexical only), the bracketed `example_sentence` as plain text (no bullets) below them, the `note` if present, and the "Linked cards" section (see Card linking). Because an `expression`'s `phrase` is much longer than a single word, the term heading wraps (`flex-wrap` + `break-words`, `text-3xl sm:text-4xl`) and every place that prints `example_sentence` keeps **`whitespace-pre-line`** so any line break survives — `cards/show.blade.php` and the search-result `<x-card>` (`components/card.blade.php`). `cards/edit.blade.php` renders `example_sentence` as a `<x-forms.textarea>` rather than a single-line input, since an expression's sentence is long.
- **Card generation variants**: `AI::getContentForCard` (bilingual, no context) and `AI::getContentForCardWithContext` write `sentence`/`examples` in the target language and `translation` in the native language, steered by the learner's CEFR level (`levelInstruction`). The **`definition` language depends on the level**: at `A1`/`A2`/`B1` (`AI::NATIVE_DEFINITION_LEVELS`) it is written in the **native** language, from `B2` up (and when no level is set) in the target language — below B2 a target-language definition is usually harder than the term it explains. This is **not** a prompt rule the model decides: `AI::definitionLanguage($level, $target, $native)` resolves it in PHP and the result is interpolated into the `definition` property description, so the model is only ever told one language to write in. The two user messages consequently say "Target language: … Native language: … Each field says which of the two it must be written in" rather than labelling the native one as translation-only. **Field-collision guard**: once the definition is native, `translation` and `definition` share a language and the model started swapping them (German `schön` → definition `hezký; krásný`, translation `To je hezké.`). `AI::fieldContrastRule()` appends one sentence to the system prompt — *"both are in X but are NOT the same: the translation is the equivalent term, the definition explains what it means"* — and is emitted **only when the two languages match**, so B2+ cards don't pay for it. The two property descriptions carry the same contrast as explicit negatives plus one worked `schön` example each (translation: "never a sentence, never an explanation"; definition: "never a translation, an equivalent word or a list of synonyms"). The **context** variant treats the supplied context as fixing *which sense/domain* of the term the card is about, so **all** fields — including every example fragment — must reflect only that meaning (e.g. "tree" in a graph-theory context → "binary tree", "spanning tree", never "climb a tree"); this constraint is stated in both its system prompt and the `examples` property description. All three methods return a JSON string with an `examples` array (mapped to the `example_1..3` columns in `AjaxController@index`, sliced to 3). `AI::getContentForCardNative` is the **monolingual** variant used when the save destination *is* the user's native language (`AjaxController@index` branches on `$language->id === $user->native_language_id`): every field is written in the native language, there is **no `translation`** (its schema omits it; the card stores `translation = ''` since the column is `NOT NULL`), and no CEFR steering is applied. It keeps the base-form `phrase` + `[term]` bracket rules and takes an optional `$context` to cover both the plain and context-supplied cases in one method.
- **Type-conditional card content**: all three generators classify **and** generate in a *single* call. `term_type` is the **first property** in every schema — strict structured outputs emit keys in schema order, so the model commits to the type before writing the fields that depend on it; this is what makes a separate classifier call unnecessary (no extra latency on the capture path). Two helpers hold the shared text so it is defined once: `AI::typeRules()` (system-prompt fragment defining the two types) and `AI::termTypeProperty()` (the `term_type` schema property). The system prompt stays short — every per-field rule lives in its property description, where each field branches on the chosen type:

  | Field | `lexical` | `expression` |
  |---|---|---|
  | `phrase` | base/dictionary form, **never bracketed** | canonical frame — pronoun + contraction kept, situation-specific tail dropped, each variable part as a **dictionary-style bracketed placeholder** `[something]` / `[someone]` / `[somewhere]` / `[do something]` (never `...`) |
  | `definition` | dictionary-style definition | **usage note** ("used to politely refuse something you have been offered") — same language rule as lexical (level-dependent, see Card generation variants) |
  | `translation` | word-level, ≤2 variants separated by `;` | **exactly one** functional equivalent — what a native speaker actually says in that situation, explicitly *not* literal, no `;`. It translates the **frame**, so a slot reappears as a placeholder **in the native language** (`[něco]`, `[etwas]`) — never the English `[something]` |
  | `sentence` | one sentence, term bracketed once | one sentence using the expression in an everyday situation, every `[something]` slot filled with **real words** and the **whole expression** bracketed once |
  | `examples` | 3 × 2-4 word collocation fragments, no final period | **empty array** — an expression is illustrated by its sentence alone |

  `examples` never contains square brackets, and the `sentence` bracket-exactly-once rule holds for **both** types, so the Sentences learning mode works for expressions too.
- **Conversation chat methods**: `AI::startConversation` (opening line), `AI::conversationReply` (per-turn in-character reply + `used_word_ids` for the learner's latest message), and `AI::conversationRecap` (end-of-chat bullet feedback) power the Conversation learning mode (see Learning flow). Unlike the card generators they take a **multi-message transcript** and use `reasoning_effort` **`low`** for the fast turns / the default constant for the recap; all three still use strict `json_schema` and the shared `levelInstruction`. Core rule enforced in the turn/opening prompts: the model must **never write the target words itself** — its job is to make the learner produce them. **Prompt caching**: `conversationReply` is structured for OpenAI's automatic prefix cache — an **invariant** system prompt (role/rules/avoid-list/level, identical every turn) sits first so the growing transcript below it is served from cache, and the only per-turn-changing piece (the shrinking remaining-words list) is a small **trailing** `system` message after the transcript. A per-chat `cache_key` (stored in `session('chat_practice')`, minted in `Learning::startConversation`) is passed to `startConversation`/`conversationReply` as `prompt_cache_key` so a chat's turns route to the same cache. Caching only kicks in above OpenAI's ~1,024-token minimum, so it mainly benefits longer chats.
- **Gap-Fill Exercises**: Dynamic learning exercises are generated using `GenerateGapFillJob`. Exercises are stored in the `gap_fill_exercises` table and include a text with numbered placeholders `[n]` and a JSON mapping of answers.
- **Background Processing**: Time-consuming AI tasks use Laravel's queue system (`GenerateGapFillJob`). UI feedback for pending tasks is handled via AJAX polling (`gap-fill.status` route).

### Models & Database
- Eloquent models are stored in `app/Models`.
- Relationships should be explicitly defined with return types.
- Mass assignment protection is typically disabled using `protected $guarded = [];`.
- **Card linking ("Linked cards")**: users manually link two of their **same-language** cards from the card detail page. Links are stored in the existing `synonyms` table (repurposed) as **two mirrored rows** per link, exposed via `Card::linkedCards()` (a `belongsToMany` self-relation through `synonyms`, `card_id`→`synonym_card_id`, `withTimestamps`). `similarity_score` is now **nullable** (manual links carry no score). Endpoints (`CardController`): `GET /cards/{card}/link-search?q=` (same-language candidates, excludes self + already-linked), `POST /cards/{card}/links`, `DELETE /cards/{card}/links/{other}` — all enforce ownership and write/remove both mirrored rows. The **automatic** embedding-based linking in `GenerateEmbeddingJob` (which populated `synonyms`/`related_terms` by cosine similarity) is **paused/commented out** (WIP) so manual links are the only source; embeddings are still generated. Re-enabling it will repopulate the same "Linked cards" table.
- Migrations follow standard Laravel naming conventions (`YYYY_MM_DD_HHMMSS_create_table_name.php`).

### Multi-language Vocabulary
- The app supports vocabulary in multiple languages. The `languages` table is a static, seeded reference list (ISO 639-1 `code`, English `name`, `native_name`, `flag`) populated by `LanguageSeeder` (idempotent on `code`); add languages there.
- A user learns **up to 5 target languages** via the `language_user` pivot (`$user->languages()`), has one `native_language_id`, and one `active_language_id` (the durable default "save" language). These FKs supersede the legacy free-text `users.target_language` / `users.native_language` columns, which are kept temporarily for backfill and dropped later.
- **Native-language vocabulary**: a user can opt to build vocabulary in their **own native language** via the "Also save words in my native language" checkbox on `/profile/edit` (under the native-language picker). Enabling it simply **attaches the native language to the same `language_user` pivot** (with `users_level` = null), so it automatically becomes a save destination and shows up in `/cards`, the Learn flow, and every place that iterates `$user->languages()` — no special code in those paths. It is kept **separate from the max-5 learning limit** (validation `max:5` applies only to `target_language_ids`, which excludes native) and is **hidden from the "Languages you are learning" table** on `/profile/edit`. `UserController@edit` derives the checkbox state (`nativeSaveEnabled`) from whether native is in the pivot and strips native out of the table data; `UserController@update` re-adds native to the sync set when the box is checked. The only save-time special-casing is the AI branch below.
- `cards`, `wordboxes`, and `themes` each carry a `language_id`. A card belongs to exactly one language; "General vocabulary" = cards in a language not attached to any wordbox.
- **Save destination**: where a new word is saved (language + optional wordbox) is chosen in the right-side picker on the dashboard and persisted in the session (`capture_language_id`, `capture_wordbox_id`) via `POST /capture-target`. `User::currentSaveLanguage()` resolves session → `active_language_id` → first target language. `AjaxController@index` reads this to set the new card's `language_id`, scope the duplicate check and themes per-language, and (optionally) attach the matching wordbox.
- The save-destination picker controls **only** where words are saved; it does not reload or re-scope the page (the dashboard itself is still cross-language by design).
- **Shared wordbox picker**: the language switcher + wordbox tag picker (general vocabulary | divider | wordbox tags + overflow "More" dropdown) is an anonymous component `<x-wordbox-picker :target-languages :wordboxes-by-language :active-language-id :heading>` (`resources/views/components/wordbox-picker.blade.php`). It owns all of its own selection/overflow JS and is page-agnostic: it exposes the current selection via `window.WordboxPicker.current()` (`{languageId, wordbox, label}`) and dispatches a `wordboxpicker:change` DOM event with the same detail on every change. Consuming pages (`setLearning`, `/cards`) read `current()` on init and listen for the event to drive their own behavior (build mode links / fetch the list). NOTE: never write the literal `<x-wordbox-picker>` tag inside a Blade `<script>` comment — Blade parses it as a real component tag.
- **Vocabulary list** (`/cards`, `CardController@index`): a single endpoint serves both the full page and live updates. It filters by `language_id` (defaults to `currentSaveLanguage()`), `wordbox` (`all|general|<id>`), `type` (see below) and two independent substring searches `term` (matches `phrase`) and `definition` (matches `definition`, `LIKE %…%`). A normal request renders `cards/index.blade.php` (the shared picker + a table whose **Term**/**Definition** column headers are live search `<input>`s, and a **Wordbox** column); an AJAX request returns JSON `{rows, pagination}` rendered from the `cards/_rows.blade.php` partial, which the page swaps into `#cardsTableBody` / `#cardsPagination` (header inputs stay put, preserving focus). Search is debounced ~250ms. Pagination links carry the current filter (`->appends()`) and are followed via AJAX. The legacy dashboard theme card links here as `GET /cards?theme=<name>` (opens the list pre-filtered to that theme, scoped to the theme's language).
- **Term-type filter** (`/cards`): a 3-option segmented control `#typeFilter` — **Lexical | Both | Expressions**, in that order, exactly one active — sits at the **left** of the same row as the bulk-action bar (which stays right-aligned). It maps to the `type` query param (`lexical` | `both` | `expression`); `both` is the default and applies no constraint, and any unrecognised value falls back to `both`. Selecting an option re-fetches the list through the same AJAX path as the other filters and is carried by pagination via `->appends()`. The type is **not** a table column — the filter is the only surface, so `cards/_rows.blade.php` keeps its 5 columns (and its hard-coded `@empty` `colspan="5"`).
- Queue jobs have no session/Auth, so they derive language from their own data (e.g. `GenerateGapFillJob` uses `$wordbox->language`).

### Learning flow
- The **Learn** nav link goes to `/setLearning`, the *card-set builder*. It is language-aware: a user picks a target language (switcher row, multi-language users only; switching toggles the wordbox list **client-side**, no DB calls), then a wordbox scope — **nothing selected = all terms in the language**, the *General vocabulary* node = terms in no wordbox, or a specific wordbox — then **Due** (default) vs **Cram**, then a learning mode (Sentences/Words/Definitions). The language switcher + wordbox list is the shared `<x-wordbox-picker>` component (see Multi-language Vocabulary).
- Selection is sent to `GET /startLearningSet/{mode}` as `language_id`/`wordbox`(`all|general|<id>`)/`scope`(`due|cram`) query params. `Learning::startLearningSet` validates ownership and stores a **structured array** in `session('learning_filter')`; `Learning::getCardsForLearning()` accepts either that array (via `getCardsForSelection`) or the legacy string filters. `due` scope caps the set at 15 when more than 20 are due (sets `more_cards_available`); `cram` returns all.
- Legacy entry points are preserved: theme cards (`/filterCardsForLearning/{theme}`) still land on `/setLearning`, which renders a simple mode picker when the session filter is a theme name; the wordbox detail page links straight to `/startLearning/{wordbox}/{mode}` (cram). `Learning::renderLearningView()` is the shared flashcard renderer for all paths.
- **Term type in the learning set**: `sentences` and `definitions` are **lexical-only** modes (`Learning::LEXICAL_ONLY_MODES`) — their fronts are a blanked example sentence and a dictionary definition, both of which only make sense for a naming unit. `Learning::modeTypeFilter($mode)` returns a closure that adds `where('term_type', '!=', expression)`, and **every** card query in `getCardsForLearning` / `getCardsForSelection` `->tap()`s it, so the constraint applies before the due-count/15-card cap rather than after (filtering the collection afterwards would have skewed the cap). `words` and `conversation` pass no mode restriction, so they keep expressions, and `lexical` cards are served by **every** mode exactly as before — the filter only ever removes expressions. Nothing else about the modes changed. There is **no frontend surface** for this yet: the mode buttons in `set.blade.php` are always offered, and the "N due cards" counts in `routes/web.php` are not mode-aware, so they can overstate what a lexical-only mode will actually serve.
- The flashcard view (`learning/index.blade.php`) shows the card's **wordbox name** in the orange pill above the card (`$card->wordbox->first()?->name`); cards in no wordbox keep the pill's space reserved but `invisible` so the layout doesn't shift. "Save and quit" is rendered as the standard back-button (arrow + text) absolutely positioned top-left so it doesn't take a full-width strip.
- In-session flow is **repeat-until-correct**: a card marked *Wrong* records `result:0` and stays in the deck (reappears) until answered *Correct*, which records `result:1` and removes it; the session ends only when the deck is empty. The "queue" counter shows the real number of remaining cards (`cards.length`), not a one-pass countdown.
- **Conversation mode** (`data-mode="conversation"`) is a fourth learning mode — a **live AI roleplay chat** (it replaced the removed "Questions" panel in `set.blade.php`, fixing the 404 that panel caused). `Learning::renderLearningView` short-circuits `conversation` to `Learning::startConversation()`, which takes **up to 10** cards from the current selection (`getCardsForLearning`), resolves the language's CEFR level (`User::levelForLanguage`), asks the AI for an opening line, seeds **ephemeral session state** `session('chat_practice')` (`{messages, target_words:[{id,term}], used_ids, stale_count, language_id, level}` — **no DB**), and renders `learning/conversation.blade.php`. The chat is **synchronous** (a jQuery `$.post` per turn, "typing…" bubble while waiting — no queue/job). Turns hit `ChatController@message`: the AI (`AI::conversationReply`) replies in character **without ever using the target words** and reports which still-remaining words the learner used (accepting misspellings/inflections, judged by the model — the reliable way vs PHP matching); the server owns the shrinking `used_ids` and `stale_count`. It **ends** when all words are used, or after **4 consecutive learner messages with no new word** (stall guard), or on manual quit. On end the client calls `ChatController@recap`: `AI::conversationRecap` returns short **bullet-fragment** feedback (per-word note, `did_well`, `corrections` — explanations in the native language, terms in the target language) shown **below** the chat, and every used word gets a **correct-review SRS bump** (`Learning::getNextStudyDay(level, 1)`, `level++`, `last_studied`, like `saveLearning`); unused words are untouched. Word-usage detection is AI-judged; the deterministic end/stall/SRS control logic stays server-side.

### Conversation Challenge (free practice chat)
- A **separate**, standalone feature (not a card learning mode and **not** tied to any wordbox/SRS): free-form conversation practice with **live per-message corrections**. Reached via the **"Conversation"** nav link → `GET /conversation` (`ChallengeController@setup`), a setup page (`challenge/setup.blade.php`) where the user picks a target language (pill picker, defaults to `currentSaveLanguage()`), reads the instruction to write in full sentences, and can optionally fill two **≤200-char** preference textareas: **Scene** (what the chat is about) and **Feedback focus** (a grammar/vocabulary point to drill, e.g. "present perfect").
- `POST /conversation/start` (`ChallengeController@start`, validates `scene`/`feedback_focus` nullable max:200) seeds **ephemeral** `session('chat_challenge')` (`{messages, struggles, language_id, level, scene, feedback_focus, scene_display, cache_key}` — **no DB, no target words**) and renders `challenge/chat.blade.php` **immediately** with a spinner (the gap-fill loader) — it does **not** block on the AI. The chat view then `$.post`s `POST /conversation/opening` (`ChallengeController@opening`), which calls `AI::startChallenge` (returns `{scene, reply}` — a short scene **label** + the pure in-character opening line, no scene-setting narration in `reply`), appends the opener to the transcript, and returns both. The client shows the `scene` in a **banner above the chat** and the `reply` as the first bubble. `opening()` is idempotent (returns the stored opener if already generated) so a refresh doesn't double it.
- The chat view has a top-left **Home** back link and a **two-column** thread: each learner message sits on the left with its **correction on the right at the same level** (Tailwind `grid md:grid-cols-2`; on mobile it stacks). The composer is an **auto-growing `<textarea>`** (Enter sends, Shift+Enter = newline), disabled until the opening loads. Synchronous `$.post` per turn to `POST /conversation/message` (`ChallengeController@message`): `AI::challengeReply` returns **both** the in-character reply **and** a correction of the learner's latest message `{has_error, is_typo, feedback}` in **one call** to save tokens. The correction is a **feedback note only** (native language, names the mistake + correct form — it does **not** echo the learner's sentence back); a green "Looks good" shows when there's no error, an orange card with the note otherwise. `scene` and `feedback_focus` steer the reply/corrections. The server appends each real mistake's `feedback` to `session('chat_challenge')['struggles']` **unless `is_typo`** — typos/fast-typing slips are excluded so they never reach the recap.
- **End of chat** (`#endBtn` → `POST /conversation/recap`, `ChallengeController@recap`): `AI::challengeRecap` turns the accumulated `struggles` (not the full transcript — token-efficient), biased by `feedback_focus`, into up to 4 **recommendations** on what to improve/learn next — only **genuine grammar/preposition/vocabulary gaps** that matter in real conversation (**typos ignored**), written in the native language as bullet fragments with **no examples** (those were the live corrections); shown below the chat, then the session state is cleared. The button becomes "Back to home".
- Prompt reuse: `AI::startChallenge`/`challengeReply` mirror the `startConversation`/`conversationReply` structure (invariant system prefix first — now also carrying the constant scene/focus — for **prompt caching**, per-chat `prompt_cache_key` = `chal-{userId}-{uuid}`, `reasoning_effort: low` on turns) but **drop all target-word elicitation**; the recap uses the default reasoning effort.

### Conversation Challenge — Voice variant (Realtime API)
- A **voice** mode of the Conversation Challenge: a live **speech-to-speech** chat on OpenAI's **Realtime API** (`gpt-realtime-2.1-mini`, `ChallengeController::REALTIME_MODEL`; default voice `marin`, `REALTIME_VOICE`). Chosen on the **same setup page** — a **Mode** pill (Text | Voice) reveals the voice-only controls (all toggled together via the `.voice-only` class): a **Turn-taking** picker (**Auto** `vad` | **Push-to-talk** `ptt`), a **Voice** dropdown (`REALTIME_VOICES` — marin/cedar/alloy/ash/ballad/coral/echo/sage/shimmer/verse), a **Speaking speed** select (0.75–1.15, maps to `audio.output.speed`), and a **barge-in** checkbox ("Let me interrupt", Auto-only → `turn_detection.interrupt_response`). Language/scene/feedback-focus inputs are reused. `POST /conversation/start` branches on `mode`: voice seeds ephemeral **`session('chat_voice')`** (`{language_id, level, scene, feedback_focus, turn_taking, voice, speed, barge_in, native_language}` — no AI call) and renders `challenge/voice.blade.php`.
- **Key architectural difference from the text mode:** the **browser talks directly to OpenAI over WebRTC** — there is **no per-turn PHP AI call**. The entire conversation behaviour lives in the session **`instructions`** string (`AI::realtimeInstructions` — persona, target language, scene, feedback focus, CEFR level via the shared `levelInstruction`). The partner stays **purely in character and gives NO live/verbal feedback** — it never corrects the learner mid-chat; all feedback is deferred to the written end-of-chat recap. Cost is **per-minute**, not per-token.
- **Endpoints:** `POST /conversation/voice/token` (`voiceToken`) mints a short-lived **ephemeral client secret** (`AI::mintRealtimeClientSecret` → `POST /v1/realtime/client_secrets`) with the session config — `instructions`, output `voice` + `speed`, **input audio transcription** (`gpt-4o-transcribe`, so the learner's speech is shown on screen), and `turn_detection`: Auto uses **`semantic_vad` with `eagerness: low`** (waits for the learner to actually finish rather than jumping in on the first pause — better for hesitant learners) plus `interrupt_response` from the barge-in toggle; push-to-talk uses `null`. The real `OPENAI_SECRET` never reaches the browser. `POST /conversation/voice/recap` (`voiceRecap`) takes the **client-collected transcript** (`[{role,text}]`) and calls `AI::voiceChallengeRecap` — since the partner gives no live feedback, this is the **only** feedback the learner gets. It mirrors the **SRS conversation recap** shape (`AI::conversationRecap`, same `AI::MODEL`) and returns three bullet-fragment lists **`{did_well, corrections, vocabulary}`** in the native language: strengths, clearly-wrong grammar (wrong→correct), and better/more-natural vocabulary. Because the input is a speech-recognition transcript, the prompt **ignores typos / mis-transcriptions / pronunciation** and never comments on spelling. Then forgets `chat_voice`. The recap panel (`challenge/voice.blade.php`) renders the three sections (green / orange / blue headings).
- **View** (`challenge/voice.blade.php`): jQuery + WebRTC — fetches the token, `getUserMedia`, `RTCPeerConnection` + mic track + `<audio autoplay>` playback + `oai-events` data channel, exchanges SDP with `POST https://api.openai.com/v1/realtime/calls`. Renders **both** transcripts live from data-channel events (`conversation.item.input_audio_transcription.completed` = learner; `response.output_audio_transcript.delta/done` = assistant) and accumulates them for the recap. Push-to-talk toggles `micTrack.enabled` and sends `input_audio_buffer.commit` + `response.create` on release; VAD keeps the mic open. **End chat** tears down the peer connection and posts the transcript to `voiceRecap`, reusing the same recap-panel markup as the text chat. WebRTC needs HTTPS — `frase.test` (Herd) qualifies.

### Conversation Challenge — Game variant (pass/fail task game)
- A **text** game mode of the Conversation Challenge: the AI runs a roleplay where **it** picks a random scene and sets the learner a **task each turn** (what information to convey), and the learner must produce it in the target language. Chosen on the **same setup page** via the **Mode** pill (Text | Voice | **Game** 🎯). Game **disallows all preferences** — selecting it hides the Scene/Feedback-focus textareas (the `.pref-block` class) and the voice-only controls; only the **language** pick and the (automatic) CEFR **level** apply. `POST /conversation/start` branches on `mode === 'game'`: seeds ephemeral **`session('chat_game')`** (`{messages, language_id, level, cache_key, current_task, survived, scene_display}` — **no preferences**) and renders `challenge/game.blade.php` (passed `maxTurns = ChallengeController::GAME_MAX_TURNS`, **10**).
- **Flow:** the view `$.post`s `POST /conversation/game/opening` (`gameOpening`) → `AI::startChallengeGame` returns `{scene, reply, suggestion}` — `scene` is a **native-language** setup, `reply` is the first in-character line (target language, spoken by a character *to* the learner), `suggestion` is the first **task**: a concise **native-language** instruction of what to convey, specific but **never prescribing a grammar structure or specific words** (e.g. "order a drink for you and your friend and ask if the pizza has vegan options"). Idempotent like `opening()`. Each turn is `POST /conversation/game/message` (`gameMessage`) → `AI::challengeGameReply(messages, task, …)` which in **one call** returns `{task_completed, has_error, mistake, reply, suggestion}`: whether the learner's latest message **accomplished the task** (A), whether it has a **clear grammar mistake or clearly wrong word** (B — typos/spelling **ignored**, same rule as the other chat modes), a short **native-language** `mistake` explanation (only when failing), and — used only on a pass — the next in-character `reply` + next `suggestion`.
- **Win/lose is decided server-side:** a **pass** = `task_completed && !has_error`. On a pass the server increments `survived`, appends the reply, and hands out the next task; on **any failure** (task not done **or** a mistake) the game **ends immediately** with `mistake` as the feedback. It also ends as a **win** after **10** cleared turns (`GAME_MAX_TURNS`). On end the result is saved to the **`challenge_game_results`** table (`ChallengeGameResult`: `user_id`, `language_id`, `turns_survived`, `completed` bool = cleared all 10) via `finishGame()`, and `chat_game` is forgotten. **No separate recap AI call** — the failing turn's `mistake` *is* the feedback (token-efficient).
- **View** (`challenge/game.blade.php`): single-column thread — assistant bubbles (left), a highlighted **"🎯 Your task"** box (native language) after each assistant line, learner replies (right) each followed by a **verdict row** of two chips (✓/✗ **Task done** + ✓/✗ **No errors**) — the "subtle pass indicator" per turn. A **Turn X / 10** counter in the header. When the game ends, a feedback panel reveals: **"🎉 You cleared all 10 turns!"** (win) or **"Game over"** + the `mistake` explanation (loss), plus **"You lasted N turns."** and Play-again / Home links. Prompt reuse: `startChallengeGame`/`challengeGameReply` mirror the challenge structure (invariant system prefix first for **prompt caching**, per-game `prompt_cache_key` = `game-{userId}-{uuid}`, `reasoning_effort: low`); the per-turn-changing task is a small **trailing** system message after the transcript.

## Frontend Patterns

### Styling
- **Tailwind CSS** is used exclusively for styling.
- Follow a "Dark Mode first" approach as the app uses a dark theme by default (`bg-black text-white`).
- Use utility classes directly in Blade files.

### Blade Components
- The project makes heavy use of anonymous Blade components located in `resources/views/components`.
- Layout: Use `<x-html-layout>` as the base wrapper.
- Forms: Use `<x-forms.*>` components (e.g., `<x-forms.input>`, `<x-forms.button>`) for consistency.
- UI Elements: Reuse components like `<x-panel>`, `<x-card>`, and `<x-section-heading>`.

### JavaScript & Ajax
- **jQuery** is used for DOM manipulation and Ajax requests.
- **Toastr** is used for notifications.
- Ajax endpoints often return JSON responses or simple status codes (e.g., `response(200)`).
- Scripts are often included directly in Blade files or managed via Vite in `resources/js/app.js`.

## Coding Standards

### PHP
- Use PHP 8+ features where appropriate (Constructor Property Promotion, Type Hints, etc.).
- Follow PSR-12 coding standards.
- Run `vendor/bin/pint` to ensure code formatting consistency.

### Naming Conventions
- Controllers: `PascalCaseController` (e.g., `CardController`).
- Models: `PascalCase` (e.g., `GapFillExercise`).
- Views: `kebab-case` or `snake_case` (e.g., `add.blade.php`, `html-layout.blade.php`).
- Components: `kebab-case` (e.g., `section-heading.blade.php`).

### Best Practices
- **Localization**: While the UI is in English, the app supports target/native language settings for users.
- **AI Integration**: Always handle AI failures gracefully (log errors, return nulls, notify user).
- **Security**: Always use `@csrf` in forms and ensure `@auth`/`@guest` checks are used in views for conditional rendering.
